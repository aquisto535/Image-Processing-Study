## 💡 알고리즘 작동 방식 상세 분석

### **1. 밝기 조절 (Brightness Adjustment) - brightness = 50**

#### **OpenCV 버전 작동 방식:**
```cpp
src.convertTo(result, -1, 1.0, brightness);
// 공식: result = src * 1.0 + 50
// 모든 픽셀 값에 50을 더함 (밝게 만듦)
```

#### **Custom 버전 작동 방식:**
```cpp
for (int y = 0; y < src.rows; y++) {
    for (int x = 0; x < src.cols; x++) {
        int val = src_ptr[x] + brightness;  // +50
        dst_ptr[x] = cv::saturate_cast<uchar>(val);  // 0-255 범위로 제한
    }
}
```

#### **실제 픽셀 변환 예시:**
```
원본 픽셀 값: [50, 100, 150, 200, 230]
결과 픽셀 값: [100, 150, 200, 250, 255] (280→255로 클리핑)
```

#### **이미지에 미치는 영향:**
- ✅ **전체적으로 이미지가 밝아짐**: 모든 픽셀에 동일한 값 추가
- ✅ **단순하고 직관적**: 전체적인 노출 보정 효과
- ⚠️ **하이라이트 손실**: 밝은 부분이 255로 클리핑되어 디테일 손실 가능

### **2. 감마 보정 (Gamma Correction) - gamma = 2.0**

#### **OpenCV 버전 작동 방식 (LUT 사용):**
```cpp
// 0~255 각 픽셀 값에 대한 변환 테이블 미리 계산
for (int i = 0; i < 256; i++) {
    lut_ptr[i] = saturate_cast<uchar>(pow(i / 255.0, 1.0 / gamma) * 255.0);
}
// 공식: output = 255 * (input/255)^(1/2.0) = 255 * sqrt(input/255)
```

#### **Custom 버전 작동 방식:**
```cpp
// 동일한 LUT 방식이지만 캐싱 최적화
for (int i = 0; i < 256; i++) {
    gamma_table[i] = saturate_cast<uchar>(
        255.0 * pow(i / 255.0, 1.0 / gamma) + 0.5
    );
}
```

#### **실제 픽셀 변환 예시 (gamma = 2.0):**
```
원본 픽셀 값: [50, 100, 150, 200, 250]
정규화(0-1):  [0.196, 0.392, 0.588, 0.784, 0.980]
제곱근 적용:  [0.443, 0.626, 0.767, 0.885, 0.990]
다시 0-255:   [113, 160, 196, 226, 252]
```

#### **감마 2.0의 효과:**
- **어두운 픽셀(0-127)**: 더 밝아짐 (대폭 증가)
- **밝은 픽셀(128-255)**: 약간 어두워짐 (소폭 감소)
- **중간톤 강조**: 전체적으로 중간톤이 밝아져서 이미지가 더 선명해 보임

#### **이미지에 미치는 영향:**
- ✅ **대비 향상**: 중간톤을 밝게 하여 이미지가 더 선명해 보임
- ✅ **자연스러운 보정**: 인간의 시각 특성에 맞춘 보정
- ✅ **디테일 보존**: 전체 톤 범위를 활용하여 정보 손실 최소화

### **3. 두 방식의 차이점**

| 항목 | 밝기 조절 | 감마 보정 |
|------|-----------|-----------|
| **보정 방식** | 선형 (모든 픽셀에 동일한 값 추가) | 비선형 (픽셀 값에 따라 다른 보정) |
| **어두운 부분** | 동일하게 밝아짐 | 크게 밝아짐 |
| **밝은 부분** | 동일하게 밝아짐 | 약간 어두워짐 |
| **대비** | 변화 없음 | 향상됨 |
| **디테일 보존** | 클리핑으로 손실 가능 | 우수 |
| **사용 목적** | 전체 노출 보정 | 톤 매핑, 대비 개선 |

### **4. 작업 완성도 평가 요약**

#### **수행된 작업:**
1. **밝기 조절**: 이미지의 전체적인 밝기를 50만큼 높임 (어두운 이미지를 밝게 보정)
2. **감마 보정**: 감마 2.0을 적용하여 중간톤을 강조해 이미지를 더 균일하고 선명하게 만듦

#### **평가 방식:**
- **OpenCV 결과를 "정답 기준"**으로 설정
- **Custom 구현이 OpenCV와 얼마나 비슷한 결과**를 만드는지 측정
- **정확도 점수**로 작업 완성도 평가

#### **현재 결과 해석:**
```
밝기 조절: 정확도 100% → Custom과 OpenCV가 완전히 동일한 품질
감마 보정: 정확도 95.19% → 매우 우수한 품질, 실질적 차이 없음
```

#### **최종 결론:**
- **작업 완성도 측면**: 둘 다 훌륭한 이미지 보정 결과 달성 ✅

**핵심:** Custom 구현도 이미지 보정 작업 자체는 완벽하게 수행했지만, 단지 속도가 느릴 뿐입니다. 이것이 바로 **"기능은 똑같이 구현했는데, 성능 최적화는 얼마나 잘 했는가?"**를 측정하는 벤치마크의 본질입니다.

## 🤔 "Raw한 접근법" 오해 분석

### **일반적인 오해: "Custom = Raw = 빠름"**

#### **C vs Python 비유의 한계:**
```
C vs Python:
Python (고수준) → 인터프리터 → C 확장 → 시스템 콜 → 하드웨어
C (저수준)     → 컴파일러 → 시스템 콜 → 하드웨어
→ C가 "더 Raw"해서 빠름 (추상화 레이어 차이)

OpenCV vs Custom:
Custom 구현 → C++ 컴파일러 → 시스템 콜 → 하드웨어  
OpenCV    → C++ 컴파일러 → 시스템 콜 → 하드웨어
→ 둘 다 같은 레벨! 추상화 차이가 거의 없음
```

### **진짜 "Raw"는 누구인가?**

#### **겉보기 Raw vs 실제 Raw:**
```cpp
// Custom 구현 (겉보기에 Raw)
for (int y = 0; y < rows; y++) {
    for (int x = 0; x < cols; x++) {
        result.at<uchar>(y, x) = src.at<uchar>(y, x) + brightness;
        // 실제로는: 함수 호출 + 범위 체크 + 1픽셀씩 처리
    }
}

// OpenCV 내부 (진짜 Raw)
uchar* src_ptr = src.ptr<uchar>(0);
uchar* dst_ptr = dst.ptr<uchar>(0);
__m128i brightness_vec = _mm_set1_epi8(brightness);

for (size_t i = 0; i <= total_pixels - 16; i += 16) {
    __m128i src_vec = _mm_loadu_si128((__m128i*)(src_ptr + i));
    __m128i result = _mm_adds_epu8(src_vec, brightness_vec);
    _mm_storeu_si128((__m128i*)(dst_ptr + i), result);
    // 16개 픽셀을 한 번에 처리하는 진짜 Raw
}
```

#### **하드웨어 활용도 비교:**
```assembly
; Custom이 생성하는 어셈블리 (1픽셀당 5개 명령어)
loop:
    mov eax, [src + offset]     ; 1바이트 로드
    add eax, 50                 ; 덧셈 연산
    mov [dst + offset], eax     ; 1바이트 저장
    inc offset                  ; 증가
    cmp offset, total_size      ; 비교
    jl loop                     ; 점프

; OpenCV SIMD (1픽셀당 0.3125개 명령어)
loop_simd:
    movdqu xmm0, [src + offset] ; 16바이트 한 번에 로드
    paddusb xmm0, xmm1          ; 16개 픽셀 동시 연산
    movdqu [dst + offset], xmm0 ; 16바이트 한 번에 저장
    add offset, 16              ; 16픽셀씩 점프
    jl loop_simd                ; 점프
```

### **성능 차이의 실제 원인:**

#### **명령어 수 비교 (512×512 이미지):**
```
Custom 구현: 1,310,720개 명령어 (1픽셀당 5개)
OpenCV SIMD: 81,920개 명령어 (1픽셀당 0.3125개)
→ 16배 차이!
```

#### **진짜 Raw Custom 구현이라면:**
```cpp
void truly_raw_brightness(const Mat& src, Mat& dst, int brightness) {
    const size_t total_pixels = src.total();
    const uchar* src_ptr = src.ptr<uchar>(0);
    uchar* dst_ptr = dst.ptr<uchar>(0);
    
    // SIMD 최적화 (OpenCV 수준)
    const __m128i brightness_vec = _mm_set1_epi8(brightness);
    size_t i = 0;
    
    // 16픽셀씩 처리
    for (; i <= total_pixels - 16; i += 16) {
        __m128i src_vec = _mm_loadu_si128((__m128i*)(src_ptr + i));
        __m128i result = _mm_adds_epu8(src_vec, brightness_vec);
        _mm_storeu_si128((__m128i*)(dst_ptr + i), result);
    }
    
    // 남은 픽셀 처리
    for (; i < total_pixels; i++) {
        dst_ptr[i] = cv::saturate_cast<uchar>(src_ptr[i] + brightness);
    }
}
// 이렇게 하면 Custom이 OpenCV보다 빠를 수 있음!
```

```cpp
for (int y = 0; y < src.rows; y++) {

        // 1. at() 함수 사용으로 범위 체크 오버헤드
        // 2. SIMD 최적화 없음
        // 3. 캐시 비효율적인 메모리 접근
        result.at<uchar>(y, x) = src.at<uchar>(y, x) + brightness;
    }
}
```

```cpp
// 좋은 예: 가로 방향 접근 (캐시 히트)

```

## 💬 추가 성능 분석 토론 (코드 레벨 상세 분석)

### **토론 주제: custom_version vs custom_optimized_version 성능 차이**

#### **분석 대상 코드:**
```cpp
// custom_version - 기본 구현
cv::Mat DualImplementationProcessor::ContrastAdjustment::custom_version(const cv::Mat& input, double contrast) {
    validateInput(input);

    int width = input.cols;
    int height = input.rows;
    int channels = input.channels();

    // Raw 데이터 추출
    unsigned char* raw_input = input.data;

    // Raw한 명암비 조절 수행
    unsigned char* raw_output = new unsigned char[width * height * channels];

    for (int i = 0; i < width * height * channels; i++) {
        double new_value = (raw_input[i] - 128) * contrast + 128;

        // Raw한 클리핑
        if (new_value > 255) new_value = 255;
        if (new_value < 0) new_value = 0;

        raw_output[i] = static_cast<unsigned char>(new_value);
    }

    // 결과를 Mat으로 변환
    cv::Mat result(height, width, input.type(), raw_output);
    cv::Mat result_copy = result.clone();

    // Raw 메모리 해제
    delete[] raw_output;

    return result_copy;
}

// custom_optimized_version - 최적화된 구현
cv::Mat DualImplementationProcessor::ContrastAdjustment::custom_optimized_version(const cv::Mat& input, double contrast) {
    validateInput(input);

    cv::Mat result = input.clone();

    if (result.isContinuous()) {
        unsigned char* data = result.data;
        int total_pixels = result.rows * result.cols * result.channels();

        for (int i = 0; i < total_pixels; i++) {
            double new_value = (data[i] - 128) * contrast + 128;

            // Raw한 클리핑
            if (new_value > 255) new_value = 255;
            if (new_value < 0) new_value = 0;

            data[i] = static_cast<unsigned char>(new_value);
        }
    }
    else {
        for (int y = 0; y < result.rows; y++) {
            unsigned char* row_ptr = result.ptr<unsigned char>(y);
            int row_pixels = result.cols * result.channels();

            for (int x = 0; x < row_pixels; x++) {
                double new_value = (row_ptr[x] - 128) * contrast + 128;

                // Raw한 클리핑
                if (new_value > 255) new_value = 255;
                if (new_value < 0) new_value = 0;

                row_ptr[x] = static_cast<unsigned char>(new_value);
            }
        }
    }

    return result;
}
```

## 🔍 성능 차이 발생 지점 상세 분석

### **1. 메모리 할당 방식의 차이 (가장 큰 병목)**

```cpp
// custom_version (느림)
unsigned char* raw_output = new unsigned char[width * height * channels];  // 동적 할당
// ... 처리 후
delete[] raw_output;  // 메모리 해제

// custom_optimized_version (빠름)  
cv::Mat result = input.clone();  // Mat의 효율적인 메모리 관리
```

**성능 영향:**
- 동적 메모리 할당/해제는 시스템 콜이 필요하여 상당한 오버헤드 발생
- `clone()`은 OpenCV 내부적으로 최적화된 메모리 할당을 사용
- **예상 성능 차이: 30-50% 향상**

### **2. Mat 객체 생성 오버헤드**

```cpp
// custom_version (느림)
cv::Mat result(height, width, input.type(), raw_output);  // 새 Mat 생성
cv::Mat result_copy = result.clone();  // 또 다른 복사 발생

// custom_optimized_version (빠름)
cv::Mat result = input.clone();  // 한 번만 복사
```

**성능 영향:**
- 두 번의 Mat 객체 생성과 메모리 복사 vs 한 번의 복사
- `custom_version`은 불필요한 중간 객체 생성
- **예상 성능 차이: 40-60% 향상**

### **3. 불필요한 메모리 복사 패턴**

```cpp
// custom_version에서 발생하는 데이터 플로우:
// 원본 데이터 → raw_output 배열 → Mat 객체 → clone된 결과
// (총 3번의 메모리 복사)

// custom_optimized_version에서의 데이터 플로우:
// 원본 데이터 → clone된 결과 (직접 수정)
// (총 1번의 메모리 복사)
```

### **4. 메모리 접근 패턴 최적화 - isContinuous()의 의미**

#### **OpenCV Mat의 메모리 저장 방식:**
```cpp
// 3x3 컬러 이미지 (3채널)의 메모리 배치 예시
// 연속 메모리일 때:
// [R1][G1][B1][R2][G2][B2][R3][G3][B3]
// [R4][G4][B4][R5][G5][B5][R6][G6][B6] 
// [R7][G7][B7][R8][G8][B8][R9][G9][B9]
// ↑ 모든 픽셀이 한 줄로 연결됨

// 비연속 메모리일 때:
// 행1: [R1][G1][B1][R2][G2][B2][R3][G3][B3] [빈공간...]
// 행2: [R4][G4][B4][R5][G5][B5][R6][G6][B6] [빈공간...]  
// 행3: [R7][G7][B7][R8][G8][B8][R9][G9][B9] [빈공간...]
// ↑ 각 행 사이에 패딩이나 gap이 존재
```

#### **연속 메모리 vs 비연속 메모리 처리:**
```cpp
// custom_version - 비효율적 접근
for (int i = 0; i < width * height * channels; i++) {
    // 문제: 비연속 메모리에서 잘못된 메모리 영역 접근 가능!
    // row1_end 이후에 padding을 건드릴 수 있음
    raw_input[i] = some_value;
}

// custom_optimized_version - 안전하고 효율적
if (result.isContinuous()) {
    // 연속 메모리: 한 번에 쭉 처리
    unsigned char* data = result.data;
    int total_pixels = result.rows * result.cols * result.channels();
    
    for (int i = 0; i < total_pixels; i++) {
        data[i] = some_value;  // 순차적 접근으로 캐시 효율 극대화
    }
} else {
    // 비연속 메모리: 행별로 안전하게 처리
    for (int y = 0; y < result.rows; y++) {
        unsigned char* row_ptr = result.ptr<unsigned char>(y);  // 각 행의 시작점
        int row_pixels = result.cols * result.channels();
        
        for (int x = 0; x < row_pixels; x++) {
            row_ptr[x] = some_value;  // 행 내에서만 접근
        }
    }
}
```

#### **중요한 발견: 연속 메모리에서의 접근 패턴 동일성**

**사용자의 지적이 정확했습니다!** 메모리가 연속적이라는 가정 하에서는:

```cpp
// custom_version
for (int i = 0; i < width * height * channels; i++) {
    double new_value = (raw_input[i] - 128) * contrast + 128;
    // ... 클리핑
    raw_output[i] = static_cast<unsigned char>(new_value);
}

// custom_optimized_version (연속 메모리일 때)
for (int i = 0; i < total_pixels; i++) {
    double new_value = (data[i] - 128) * contrast + 128;
    // ... 클리핑  
    data[i] = static_cast<unsigned char>(new_value);
}
```

**둘 다 순차적으로 한 바이트씩 접근하는 동일한 패턴입니다.**

#### **그렇다면 진짜 성능 차이는?**

| 구분 | custom_version | custom_optimized_version |
|------|----------------|-------------------------|
| **메모리 접근 패턴** | 순차 접근 (동일) | 순차 접근 (동일) |
| **메모리 할당** | `new[]` + `delete[]` (느림) | Mat 내부 관리 (빠름) |
| **데이터 복사** | 3회 (매우 느림) | 1회 (빠름) |
| **객체 생성** | Mat 2개 생성 (느림) | Mat 1개 생성 (빠름) |

**결론**: 메모리 접근 패턴 자체는 동일하지만, **메모리 관리 방식의 차이**가 2-3배의 성능 차이를 만듭니다.

## 🧠 OpenCV Mat의 고급 메모리 관리 기법

### **1. clone()의 깊은 복사 특성**

```cpp
cv::Mat original = // 원본 이미지
cv::Mat copied = original.clone();  // 깊은 복사 실행
```

**깊은 복사 특징:**
1. **새로운 메모리 공간 할당**: 원본과 완전히 분리된 메모리 영역 생성
2. **데이터 완전 복사**: 모든 픽셀 데이터를 새 메모리에 복사
3. **독립적 객체**: 원본과 복사본이 서로 영향을 주지 않음

**다른 복사 방식과 비교:**
```cpp
cv::Mat original = // 원본 이미지

// 1. 얕은 복사 (shallow copy) - 데이터 공유
cv::Mat shallow = original;  // 같은 데이터를 가리킴

// 2. 깊은 복사 (deep copy) - 완전히 독립적
cv::Mat deep = original.clone();  // 새로운 데이터 메모리

// 3. 조건부 복사
original.copyTo(deep);  // clone()과 동일한 효과
```

### **2. 이동 생성자 활용 (C++11 이후)**

**OpenCV 3.0 이후부터 `cv::Mat` 클래스는 이동 의미론을 지원합니다:**

```cpp
// 이동 생성자 사용
cv::Mat createImage() {
    cv::Mat temp(480, 640, CV_8UC3);
    // ... 이미지 처리
    return temp;  // 이동 생성자로 반환 (복사 없음)
}

cv::Mat result = createImage();  // 이동 생성자 호출

cv::Mat img1 = cv::imread("image.jpg");
```

**이동 의미론을 활용한 최적화:**
```cpp
cv::Mat optimized_move_version(cv::Mat input, double contrast) {  // 값으로 받아서 이동 활용
    validateInput(input);
    
    // input을 직접 수정 (이미 이동된 상태)
    if (input.isContinuous()) {
        unsigned char* data = input.data;
        int total_pixels = input.rows * input.cols * input.channels();
        
        for (int i = 0; i < total_pixels; i++) {
            double new_value = (data[i] - 128) * contrast + 128;
            data[i] = static_cast<unsigned char>(std::clamp(new_value, 0.0, 255.0));
        }
    }
    
    return input;  // 이동 반환
}
```

### **3. 원본 보존 전략에 따른 메모리 관리**

#### **원본 유지가 필요한 상황별 최적 선택:**

| 상황 | 접근법 | 이유 |
|------|-------|------|
| **원본 + 처리본 모두 필요** | `clone()` 사용 | 데이터 안전성 보장 |
| **멀티스레드 환경** | `clone()` 사용 | 스레드 안전성 |
| **한 번만 처리** | 이동 의미론 활용 | 성능 최적화 |
| **분석만 수행** | `const` 참조 사용 | 불필요한 복사 방지 |
| **조건부 보존** | 매개변수로 제어 | 유연성 확보 |

#### **지연 복사 (Lazy Copy) 패턴:**
```cpp
class SmartImageProcessor {
    cv::Mat original;
    mutable cv::Mat working_copy;  // 필요할 때만 생성
    mutable bool copy_created = false;
    
public:
    cv::Mat& getWorkingCopy() const {
        if (!copy_created) {
            working_copy = original.clone();  // 필요한 시점에 복사
            copy_created = true;
        }
        return working_copy;
    }
};
```

## 🏆 CPU 캐시와 메모리 지역성 최적화

### **1. 캐시 친화적 접근의 이점**

```cpp
// CPU 캐시는 연속된 메모리 블록을 가져옴
// 캐시 라인 크기: 보통 64바이트 (16개의 int 또는 64개의 char)

// ❌ 캐시에 비친화적
for (int y = 0; y < height; y++) {
    for (int x = 0; x < width; x++) {
        for (int c = 0; c < channels; c++) {
            // 픽셀별로 채널을 건너뛰며 접근
            img.at<cv::Vec3b>(y, x)[c] = value;  // 비효율적
        }
    }
}

// ✅ 캐시에 친화적
if (img.isContinuous()) {
    unsigned char* data = img.data;
    for (int i = 0; i < total_elements; i++) {
        data[i] = value;  // 순차 접근으로 캐시 히트율 극대화
    }
}
```

### **2. 메모리 지역성 최적화 실제 효과**

```cpp
// 비연속 메모리에서 안전한 접근
void processNonContinuousImage(cv::Mat& img) {
    for (int y = 0; y < img.rows; y++) {
        // 각 행의 실제 데이터 포인터 획득
        unsigned char* row_data = img.ptr<unsigned char>(y);
        
        // 해당 행 내에서만 순차 접근
        for (int x = 0; x < img.cols * img.channels(); x++) {
            row_data[x] = process(row_data[x]);
            // ↑ 이 방식이 캐시에 친화적이면서도 안전함
        }
        // 다음 행으로 넘어갈 때만 포인터 점프
    }
}
```

### **3. isContinuous() 체크의 진짜 가치**

**핵심 포인트:**
1. **메모리 구조에 맞는 최적 접근법 선택**
2. **순차 접근**: CPU 캐시가 연속된 데이터를 미리 로드
3. **행별 처리**: 비연속 메모리에서 안전성과 성능 둘 다 확보
4. **메모리 지역성**: 가까운 위치의 데이터를 연속해서 접근할 때 캐시 효율 극대화

**결과**: 같은 연산을 해도 메모리 접근 패턴에 따라 **2-3배의 성능 차이** 발생 가능!

## 📋 성능 차이의 본질: 객체 복사 과정 분석

### **최종 결론: 객체 복사 패턴이 성능 차이의 핵심**

지금까지의 분석을 통해 확인된 것은 **실제 이미지 처리 연산은 동일하지만, 객체 복사 과정에서 성능 차이가 발생**한다는 것입니다.

### **1. 복사 과정 비교 다이어그램**

#### **custom_version: 3단계 복사 과정 🐌**
```
원본 이미지 데이터
    ↓ (1번째 복사)
raw_output 배열 (new[] 할당)
    ↓ (2번째 복사)  
Mat 객체 생성
    ↓ (3번째 복사)
clone된 최종 결과
```

#### **custom_optimized_version: 1단계 복사 과정 ⚡**
```
원본 이미지 데이터
    ↓ (1번째 복사)
clone된 최종 결과 (직접 수정)
```

### **2. 복사 비용 상세 분석 표**

| 단계 | custom_version | custom_optimized_version | 차이점 |
|------|----------------|-------------------------|---------|
| **1단계** | `new[]` 배열 복사 | `clone()` 한 번 | new[] vs Mat 내부 관리 |
| **2단계** | 포인터 연결 (Mat 생성) | (생략) | 불필요한 중간 객체 |
| **3단계** | `clone()` 또 한 번 | (생략) | 중복 복사 |
| **총 메모리 복사** | **3번** | **1번** | **3배 차이** |
| **동적 할당 횟수** | **2번** (new + clone) | **1번** (clone만) | **2배 차이** |
| **시스템 콜 호출** | **3번** (new, clone, delete) | **1번** (clone만) | **3배 차이** |

### **3. 메모리 관리 방식 비교**

#### **custom_version의 메모리 관리:**
```cpp
// 1. 동적 할당 (시스템 콜 1)
unsigned char* raw_output = new unsigned char[size];

// 2. 데이터 복사 1 (메모리 copy 1)
for (int i = 0; i < total; i++) {
    raw_output[i] = processed_value;
}

// 3. Mat 객체 생성 (포인터 연결)
cv::Mat result(height, width, input.type(), raw_output);

// 4. 추가 복사 (시스템 콜 2 + 메모리 copy 2)  
cv::Mat result_copy = result.clone();

// 5. 메모리 해제 (시스템 콜 3)
delete[] raw_output;
```

#### **custom_optimized_version의 메모리 관리:**
```cpp
// 1. 복사와 동시에 작업 공간 확보 (시스템 콜 1 + 메모리 copy 1)
cv::Mat result = input.clone();

// 2. 직접 수정 (추가 복사 없음)
for (int i = 0; i < total; i++) {
    result.data[i] = processed_value;
}

// 3. 반환 (복사 없음)
return result;
```

### **4. 성능 차이 원인 우선순위 표**

| 순위 | 원인 | custom_version 비용 | custom_optimized_version 비용 | 영향도 |
|------|------|-------------------|------------------------------|--------|
| **1위** | **불필요한 메모리 복사** | 3번 복사 | 1번 복사 | ★★★★★ |
| **2위** | **동적 할당/해제 오버헤드** | new[] + delete[] | Mat 내부 관리 | ★★★★☆ |
| **3위** | **중간 객체 생성** | Mat 2개 생성 | Mat 1개 생성 | ★★★☆☆ |
| **4위** | **시스템 콜 횟수** | 3번 호출 | 1번 호출 | ★★★☆☆ |
| **5위** | **메모리 접근 패턴** | 동일 | 동일 | ★☆☆☆☆ |
